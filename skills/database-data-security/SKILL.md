# Database and data security

Use this skill for application database code, schema and migration reviews, data-layer security design, or scoped database configuration reviews. Keep recommendations specific to the database engine, version, application, and deployment. This skill does not establish that a system is secure or compliant.

## Procedure

1. **Set the scope.** Identify the repository paths or database configuration, engine and version, affected environment, relevant data, and the requested outcome. If these are not evident, state what can be reviewed from the available artifacts and what deployment facts are missing.
2. **Trace the data path and schema.** Follow representative reads and writes from input through query construction, authorization, storage, logging, and backup or export paths. Inspect schema types, nullability, defaults, uniqueness, foreign keys, and other constraints against application invariants. Check that values use parameterized queries and that dynamic identifiers or sort clauses are allowlisted. A bound query does not itself enforce authorization.
3. **Review application transaction behavior.** Inspect transaction boundaries, atomicity, isolation assumptions, lock scope, concurrency, retry/idempotency behavior, and whether failures can leave partial state. Relate these to schema constraints and migrations; distinguish source review from runtime database behavior.
4. **Review identity and privileges.** Locate database identities, credential-source references, and access boundaries without retrieving raw credential values. Look for least-privilege application roles, separation between environments and duties where appropriate, protected remote connections, and avoidance of a superuser as the normal application identity. Do not expose credential values in notes or findings.
5. **Review password storage separately from other secrets.** Passwords should be salted and adaptively hashed with a maintained password-hashing library; they should not be stored as plaintext or reversibly encrypted. Check the selected algorithm, salt and work-factor metadata, framework/library use, target-environment cost, and login throttling where visible. Do not propose a custom hashing routine. Treat a pepper or other verifier secret as optional and keep it separate from stored hashes. NIST's password guidance is specific to its stated digital-identity context; OWASP's algorithm parameters are guidance, not a universal legal or product mandate.
6. **Review encryption and key handling against a threat model.** Identify what is encrypted, at which layer, who can decrypt it, and which exposure the layer addresses. Do not treat disk or database at-rest encryption as protection from an application or host identity that can read both the data and decryption key. Check that keys are not hard-coded or committed alongside protected data; assess a managed key/secrets service or equivalent separation where appropriate. For envelope encryption, distinguish the data-encryption key from the separately protected key-encryption key. Consider rotation, recovery, compromise response, and whether retained backups still need old keys. A vault or KMS is an option with availability and recovery costs, not a default requirement.
7. **Review migrations and recovery.** Inspect migrations for destructive changes, lock duration, rolling-deployment compatibility, transactional behavior, and a recovery path. For backups, establish method, encryption, access, retention, and intended recovery objectives from evidence or supplied facts. A successful backup job does not prove recoverability; verify that the documented restore path has been exercised. Do not run a restore against a live target or apply a migration as part of a review.
8. **Report actionable findings.** Prefer a small, evidence-backed change. Include verification that covers a relevant negative or boundary case, plus the files, environments, database features, and runtime behavior not examined.

## Evidence and coverage

- Read [Database, Encryption, and User Data Research](../../research/DATABASE_DATA_PRIVACY_RESEARCH.md), especially sections 2–5, when choosing checks or explaining tradeoffs. Use [Reference Projects](../../research/REFERENCE_PROJECTS.md) section “What is worth combining” for tool-scope and coverage principles. Follow the shared [finding and action contract](../../references/finding-contract.md) for reports, evidence language, and action boundaries.
- Point findings to exact files and lines, SQL/configuration, schema objects, or observed settings. Quote only the minimum useful evidence and redact secrets and personal data.
- Separate source-code evidence from deployment settings and runtime behavior. Say “not observed in the inspected scope” when review coverage is partial. Do not turn an absent pattern match into proof that a control is absent.
- Name the engine/version, paths, roles, migrations, environments, tools, and live checks actually examined; list material gaps. A code-only review cannot establish effective production privileges, backup recoverability, key isolation, or encryption configuration.
- Explain practical impact and the conditions required for it. Do not assign false precision to severity or claim that a scan or checklist proves security.

## Action boundaries

Repository inspection and non-invasive local analysis may proceed within the requested scope. Before changing production data, database privileges, backups, key-management settings, infrastructure, or another person's system, establish the exact target, impact, and rollback/verification plan, and obtain explicit authorization. Active checks against any running database—including local or isolated targets—also require the exact scope and impact/rate/time limits in the shared contract. A local-fix request alone does not authorize package scripts, migrations, restores, or other effectful commands. Never read or export actual key material; review key-management settings and metadata only. Never apply migrations, run write-capable query plans such as `EXPLAIN ANALYZE` on writes, restore backups, change access rules, or rotate live keys without separate explicit authorization. Never test, validate, or attempt to use discovered credentials in any environment. Never display, copy, or export secrets or actual key material in outputs, logs, diffs, tool results, or external queries.
